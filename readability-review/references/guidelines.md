# Readability Guidelines — full checklist

Source: https://readabilityguidelines.co.uk/readability-checklist/
Maintained by Content Design London. The wiki was last updated in 2020 but remains the canonical evidence-based reference.

When reviewing a document, work through these in order. Each rule has an ID (G1–G83) — use these IDs in the report so issues are traceable.

---

## A. Clear language

### Plain English
- **G1** — Choose easy and short words, not formal long ones. (e.g. "use" not "utilise", "buy" not "purchase")
- **G2** — Avoid jargon and buzzwords; they're rarely clear language.
- **G3** — Write conversationally, in first person, using the active voice.
- **G4** — Test content with users (note this in the report as a recommendation, not a defect).

### Simple sentences
- **G5** — Average sentence length should be around 15 words. Flag if the average is well above this, or if any individual sentence is excessively long (>25 words is a strong signal).
- **G6** — Avoid complex sentence structures (multiple clauses, nested subclauses, parenthetical asides that derail the main thought).

### Specialist terms
- **G7** — Explain specialist terms; assume any reader could land on this content.
- **G8** — Write so all users can understand, regardless of expertise.
- **G9** — Help users understand specialist terms (define on first use, link to a glossary, or use plain alternatives).
- **G10** — Use plain English even for highly literate audiences — evidence shows experts also prefer it.

### Legal, medical, financial terms
- **G11** — Use simple language for legal terms.
- **G12** — Explain the law in context.
- **G13** — Write medical information clearly.
- **G14** — Explain medical terms.
- **G15** — Use clear language for financial information.
- **G16** — Explain financial terminology.
- **G17** — Give examples of conceptual financial arrangements.

### Words to avoid
- **G18** — Never use vague words and jargon. Examples to flag: "leverage", "synergy", "robust", "going forward", "stakeholder" (without context), "best practice", "deliverables".
- **G19** — Avoid metaphors. They translate poorly and confuse non-native speakers.
- **G20** — Don't use Latin. Replace "i.e." with "that is", "e.g." with "for example", "etc." with "and so on" (or rewrite the sentence).

## B. Grammar points

### Abbreviations and acronyms
- **G21** — No points or spaces in abbreviations (write "UK" not "U.K.", "BBC" not "B.B.C.").
- **G22** — Write "for example" and "that is" in full instead of "e.g." / "i.e." (overlap with G20).
- **G23** — Test with users to learn how familiar your audience is with each abbreviation.
- **G24** — If an acronym is better understood than its expansion, use the acronym (e.g. "NASA", "BBC").
- **G25** — Use all caps for initialisms (each letter pronounced separately: "BBC", "FBI").
- **G26** — Capitalise only the first letter for acronyms pronounced as words ("Nasa", "Unicef" — though common style varies; consistency matters most).
- **G27** — Capitalise single letters in expressions (e.g. "U-turn", "X-ray").
- **G28** — Provide full text explanations on first use.
- **G29** — Consider repeating the full explanation each time, especially in long content where readers may skim in.

### Contractions
- **G30** — Avoid negative contractions ("do not" rather than "don't", "cannot" rather than "can't") — they're easier to misread.
- **G31** — Simple positive contractions ("you'll", "we're") are usually fine.
- **G32** — Possessive nouns are fine.
- **G33** — Avoid conditional contractions ("you'd", "they'd") — ambiguous and harder to parse.

### Hyphens and dashes
- **G34** — Only use a hyphen if the word is confusing without it.
- **G35** — Don't use hyphens for date or time ranges; use "to" ("9am to 5pm", not "9am-5pm").
- **G36** — Keep hyphen usage current (many compounds have lost their hyphens — "email", "online").
- **G37** — Be consistent across the document.
- **G38** — Avoid dashes whenever possible.
- **G39** — If a dash is needed, use an en-dash (–), not a hyphen (-) or em-dash (—).

### Capital letters
- **G40** — Don't capitalise whole words or phrases for emphasis.
- **G41** — Use sentence case in headlines and subheads (not Title Case).
- **G42** — Use sentence case for buttons.
- **G43** — Proper nouns are an exception (capitalise as normal).
- **G44** — Don't capitalise terms unless they're proper nouns ("government", not "Government").

### Ampersands
- **G45** — Use "and", not "&", in body text.

### Numbers
- **G46** — Use numerals, not words (write "5" not "five"). Note: this contradicts AP/Chicago style; the evidence here is about scanability.
- **G47** — Choose clear typography (numerals must be unambiguous in the chosen font).
- **G48** — Be specific with data (avoid "many", "several", "a few" when a number is known).
- **G49** — Use percentages where they aid comprehension.
- **G50** — Use "to" for number ranges, not a hyphen ("10 to 20", not "10-20").
- **G51** — Use years and months together rather than just months for durations longer than a year.
- **G52** — Use a space before KB and MB ("5 MB", not "5MB").
- **G53** — Spell out the month in dates; write the day as a numeral without "st", "nd", "th" ("3 May", not "3rd May" or "May 3rd").

## C. Audiences, devices, channels

### Talking to your audience
- **G54** — Make it clear who "we" and "you" refer to.
- **G55** — Be consistent — don't switch between first/second/third person.
- **G56** — Decide upfront how you'll refer to third parties.

### Writing about people
- **G57** — Use respectful terms for disability, mental health, and dying.
- **G58** — Don't reference age unless it's relevant.
- **G59** — Don't reference gender unless it's relevant.
- **G60** — Don't reference medical, mental, or cognitive condition unless relevant.
- **G61** — Don't reference heritage or nationality unless relevant.
- **G62** — Use "inclusive" or "accessible" for things designed to provide an equal experience.

### Mobiles and tablets
- **G63** — Design for mobile first (relevant when reviewing layout, not just text).
- **G64** — Always ask "how would this look on mobile?"
- **G65** — Put calls to action close to the content they relate to.
- **G66** — Test content with people using mobiles.

### Social media
- **G67** — Capitalise the first letter of each word in hashtags ("#ReadabilityGuidelines", not "#readabilityguidelines") — improves screen reader pronunciation.
- **G68** — Use image description (alt text) functions.
- **G69** — Describe GIFs in the post text.
- **G70** — Caption videos and multimedia.

## D. Content design specifics

### Links
- **G71** — Make link text meaningful — never "click here" or "read more".
- **G72** — Avoid mid-sentence links.
- **G73** — Front-load link text (most important word first).
- **G74** — Make CTA link and button text specific.
- **G75** — Start CTA links and button text with a verb.
- **G76** — Keep CTA links and button text 2 to 4 words.
- **G77** — Link text should match the destination content (page title or first heading).
- **G78** — Use sentence case for links.

### Headings, titles
- **G79** — Use specific, meaningful headings.
- **G80** — Front-load headings (key word first).
- **G81** — Structure pages with a logical heading hierarchy (H1 → H2 → H3, no skipping).
- **G82** — Use sentence case for headings and subheadings.
- **G83** — Label headings (use heading styles, not just bold text — important for accessibility).

## How to use this reference

When generating a report:
1. Read through the document and identify which guidelines are violated, with concrete evidence (a quote or location).
2. Skip rules that don't apply to the document's medium (e.g. ignore G63–G70 for an internal report; ignore G71–G78 if there are no links).
3. Group findings by section (A/B/C/D) so similar issues cluster.
4. For each issue, cite the guideline ID so the user can look it up.
5. Don't list rules the document follows correctly — only what needs fixing. (Exception: if the user asks for full coverage.)

## Rules that need data, not eyeballs

Some checks benefit from a calculation rather than a guess:
- **G5** (sentence length) — compute the average word count per sentence and the maximum sentence length. If average > 18 or any sentence > 25 words, flag it.
- **G6** (complexity) — count clauses or look for sentences with 3+ commas as a proxy.
- Reading-level scores (Flesch–Kincaid, etc.) aren't part of the guidelines but can be a useful supplementary signal — mention them only if the user asks.

If the document is long enough that you have access to code execution, write a quick Python script to compute these. Otherwise eyeball the longest few sentences.
